Coding Agent Workflow Plugin

让 AI 先读对上下文，再计划、实现、沉淀。

cuberhyk-dev-flow 把大型项目里的 AI 协作拆成三个清晰动作： 进入上下文、制定可验证计划、沉淀长期知识。它不追求复杂方法论， 只提供一条稳定的小循环。

查看安装命令 查看开发流程

安装方式

当前推荐先用本地 marketplace 安装；npm 发布完成后再切换到 npx。

Claude Code 本地安装 
claude plugin marketplace add "C:\Users\胡运宽\plugins\dev-flow"
claude plugin install cuberhyk-dev-flow@cuberhyk-plugins
claude plugin list
Codex 本地插件 
cd C:\Users\胡运宽\plugins\dev-flow
node .\bin\dev-flow.js install
npm 发布后的安装 
npx cuberhyk-dev-flow install

项目初始化

新项目接入 cuberhyk-dev-flow 时，先创建最小记忆结构，再用校验命令检查文档归位。

创建目录和入口文档

生成 CONTEXT.md、docs/ai/context-map.md、capabilities、plans、audits、adr 等目录；已有文件不会被覆盖。

检查文档路由

检查缺失目录、计划/审查缺状态、capability 误放审查报告、context-map 是否默认指向历史材料。

初始化与校验 
npx cuberhyk-dev-flow init-project /path/to/project
npx cuberhyk-dev-flow validate-docs /path/to/project

三个技能

每个技能只做自己的事，避免一个命令同时读上下文、写计划、改代码、写报告。

dev-orient

进入上下文

用于新会话或非平凡任务开始前，确认仓库、规则、文档入口、相关代码和产物归位。

  • 检查 git 状态
  • 读取 AGENTS、CONTEXT、context-map
  • 选择相关 capability 文档
  • 提示是否进入 dev-plan
  • 识别计划、审查、ADR 的存放位置

dev-plan

制定计划

用于把已经明确方向的任务收敛成可执行、可验证、范围清晰且产物归位明确的开发计划。

  • 明确目标和非目标
  • 列出风险和不确定点
  • 拆分最小步骤
  • 定义验收方式
  • 计划文档写入 docs/plans

dev-distill

沉淀知识

用于任务完成后，按类型把稳定知识、审查报告、计划记录、ADR 或测试归位。

  • 更新领域词汇
  • 更新 capability 文档
  • 审查报告写入 docs/audits
  • 记录重要取舍
  • 建议补充测试

目录规则

三个技能都遵守同一套知识归位规则，避免计划、审查报告和长期事实混在一起。

内容类型 存放位置 规则
项目规则与 AI 行为约束 AGENTS.md 或 CLAUDE.md 命令、代码风格、分支约束、上下文启动方式。
稳定领域词汇 CONTEXT.md 只放长期概念，不放任务结论或审查过程。
AI 上下文路由 docs/ai/context-map.md 说明不同任务要读哪些 capability 和代码入口。
当前模块事实 docs/capabilities/*.md 只描述当前推荐实现、事实源、API、数据表和测试方式。
计划文档 docs/plans/*.md dev-plan 需要持久化计划时写这里，不写入 capabilities。
审查报告与问题清单 docs/audits/*.md 审查产物写这里；只有稳定事实才由 dev-distill 同步到 capability。
已蒸馏审查历史 docs/audits/archived/*.md 保留证据链但不进入默认上下文；需要追溯时才读取。
重要决策 docs/adr/*.md 只记录难反悔、有取舍、未来维护者会追问原因的决定。
可执行规则 测试 回归风险高的业务规则优先落到测试，而不是只写自然语言。

产物生命周期

写文档不是终点。任务结束时要关闭计划和审查产物，避免历史材料变成默认事实。

产物 状态流转 收尾规则
Plan active -> completed / superseded / archived 实现和验证完成后，由 dev-distill 标记完成或过期。
Audit active -> distilled / archived / delete 稳定事实进入 capability、ADR 或测试后，审查报告归档或删除。
Capability current only 只保留当前事实源、规则、入口和测试方式，不保留调查过程。
ADR proposed -> accepted / superseded / deprecated 只有难反悔且有真实取舍的决定才写 ADR。

功能开发流程

需求越大，越应该完整走一遍；小修小补可以跳过 dev-plan，但不要跳过基本上下文确认。

1

Orient

先确认项目事实和相关入口。

2

Plan

把需求变成目标、步骤、风险、验收和产物归位。

3

Implement

按计划做最小必要修改并验证。

4

Distill

把稳定知识沉淀到文档或测试，并关闭历史产物。

一次典型功能开发 
/cuberhyk-dev-flow:dev-orient 我要开发学习统计的连续学习天数
/cuberhyk-dev-flow:dev-plan 基于刚才上下文制定实现计划
按照计划实现并运行验证
/cuberhyk-dev-flow:dev-distill 本次实现完成，请沉淀长期知识

怎么判断该用哪个

这套插件不是替代讨论，而是把讨论后的开发过程固定下来。

需求还模糊

先和 AI 讨论或 brainstorm。等方向清楚后，再使用 dev-orient 进入项目事实，再用 dev-plan 收敛。

需求已经明确

直接从 dev-orient 开始。它会告诉你该读哪些文档和代码， 并判断下一步是否需要 dev-plan。

维护规则

长期项目最怕文档越堆越多。cuberhyk-dev-flow 只保留可复用的稳定知识。

  • ✓ 领域术语写入 CONTEXT.md，不要散落在一次性报告里。
  • ✓ 模块职责、事实源、入口和测试方式写入 docs/capabilities/*.md。
  • ✓ 重要且难反悔的取舍写入 docs/adr/*.md。
  • ✓ 可执行规则优先沉淀为测试，而不是只写自然语言说明。
推荐心法：过程性 plan、todo、审计报告可以存在，但不要让它们成为新会话默认上下文。 默认上下文只放当前事实、稳定术语、模块边界和验证入口。
