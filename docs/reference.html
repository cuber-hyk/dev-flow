技能边界、文档路由和生命周期规则

这里记录 Dev Flow 的稳定协议。实现者可以用它判断产物应该放哪里、什么时候归档、什么时候写 ADR 或 CHANGELOG。

技能职责 框架图 技能页面 Output templates 文档路由 生命周期 ADR 门控 CHANGELOG

技能职责

每个技能只负责一个阶段。模糊需求先用 dev-brainstorm 澄清；大文件或模块边界风险先用 dev-split 判断；明确任务再使用 dev-plan 和 dev-branch。

技能负责不负责
dev-init创建最小项目记忆结构。推断完整项目知识。
dev-check检查文档路由、生命周期、git 可见性。深度业务审查。
dev-orient低噪声进入仓库上下文。计划、审查、实现或沉淀。
dev-brainstorm澄清模糊想法、比较路线并确认决策。写可执行计划、审查 findings 或实现代码。
dev-design-system初始化、更新或检查项目级 UI 设计契约与语义复用规则。预测未出现的 UI 场景或替代组件实现。
dev-split评估大文件、模块边界和代码放置风险，给出拆分方案或约束。未经批准直接实现代码或追求行数目标。
dev-plan内置 orient gate，识别决策点，制定计划。实现或归档知识。
dev-audit内置 orient gate，输出证据化发现。修复问题。
dev-exploratory-review开放式风险发现，建立项目地图与风险地图，只报告真实失败路径。实现修复或评论风格偏好。
dev-branch分支实现、验证、生命周期 gates、独立评审和审批评审。静默混入无关改动、跳过评审或自动 push。
dev-changelog维护面向人的发布说明。记录每个 commit 或内部微调。
dev-distill沉淀长期知识并关闭过程产物。重新规划、重新审查或实现。

框架图

Dev Flow 的技能分成四层：入口理解、专项判断、计划实现、收尾沉淀。智能代理不应该把这些职责混在一个步骤里。

技能分层架构

入口理解dev-orient、dev-brainstorm：进入上下文，澄清目标、非目标和用户决策。
专项判断dev-design-system、dev-split、dev-audit、dev-exploratory-review：处理 UI 规则、模块边界、审查和风险发现。
计划实现dev-plan 汇总确认路线；dev-branch 在分支内实现、验证和评审。
收尾沉淀dev-changelog、dev-distill、dev-check：更新发布说明、长期知识和生命周期状态。

常见依赖路径

功能开发
dev-brainstorm->dev-plan->dev-branch
结构治理
dev-split->dev-plan->dev-branch
UI 规则
dev-design-system->dev-plan->dev-branch
问题修复
dev-audit->dev-plan->dev-branch
生命周期
dev-branch->dev-changelog->dev-distill->dev-check

输出模板

每个技能都有独立的最终响应模板，位置是 skills/<skill>/templates/output.md。SKILL.md 定义行为和门控；templates/output.md 定义代理在技能结束时应该使用的响应形状。

dev-orientskills/dev-orient/templates/output.md已加载上下文、入口、事实源、产物目的地。

dev-planskills/dev-plan/templates/output.md可计划输出和被决策阻塞输出。
dev-auditskills/dev-audit/templates/output.md范围、带编号和状态的问题、证据、验证、路由。
dev-exploratory-reviewskills/dev-exploratory-review/templates/output.md范围、项目地图、风险地图、验证轮次、可追踪问题、探针。

文档路由

计划、审查、长期事实和决策必须分开存放。capability 只保留当前事实，不存调查过程。

CONTEXT.md

稳定领域词汇和长期业务概念。

docs/ai/context-map.md

任务到 capability、代码入口和产物目录的路由。

docs/capabilities/

当前模块事实、事实源、入口和验证方式。

docs/plans/

仍在驱动当前任务的 active 计划。

docs/audits/

审查报告和未关闭 findings。

docs/adr/

proposed 或 accepted 的长期决策。

生命周期规则

completed 和 distilled 是事件，不是最终状态。被替代内容如果有历史价值就归档，否则删除。Audit 只有在 findings 全部验证、接受风险、不处理、不可复现或明确转入 plan 后才能归档。

计划
活跃->归档或删除
审查
活跃直到所有问题关闭->归档/删除
能力文档
仅保留当前事实->原地更新
ADR
提议->接受->归档或删除

ADR 门控

ADR 只记录重要、长期、难反悔且有真实取舍的决策。用户不需要每次提醒，dev-distill 必须主动判断。

应该写 ADR

改变事实源、架构路线、数据库迁移策略、长期算法政策、跨模块规则或重大功能取舍。

不应该写 ADR

普通 bug 修复、小 UI 调整、局部重构、一次性审查结论或没有真实备选方案的修正。

状态

只使用 proposed、accepted、archived。不使用 superseded 或 deprecated。

CHANGELOG 规则

更新日志是面向人的发布说明，不是 commit log。dev-branch 在审核前判断是否需要写入。

分类使用场景
Added新增功能、命令、技能、API 或公开能力。
Changed用户可见行为、默认值、安装、配置、兼容性或工作流变化。
Deprecated仍可用但不推荐继续使用的功能、API 或行为。
Removed移除的功能、命令、配置、文件或行为。
Fixed影响用户、业务结果、数据正确性、安装或运行的修复。
Security鉴权、权限、密钥处理或数据暴露相关修复。
