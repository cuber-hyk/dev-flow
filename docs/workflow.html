Workflow

从模糊需求到可审核合并

Dev Flow 把任务拆成一组 gate。每个 gate 都有明确职责，避免 AI 跳过决策、混入无关改动或把一次性报告当成长期知识。

日常开发 审查驱动 分支闭环 审核输出

日常开发：plan -> branch

用户只提出任务。`dev-plan` 负责进入上下文、识别决策点、创建计划；`dev-branch` 负责实现、验证和审核前收尾。

Plan
/dev-plan->Orient Gate->Decision Gate->Plan file or chat plan
Build
/dev-branch->Task branch->Implement->Verify
Close
Changelog Gate->Distill Gate->Check Gate->Review Gate->Approve

审查驱动：audit -> plan -> branch

当任务是“看看哪里不对”时，先审查，不要直接写计划。审查报告只放在 `docs/audits/`，稳定事实由后续 distill gate 同步到长期文档。

1
/dev-audit

内置 orient gate，定义范围、读取证据、输出 findings。非平凡审查写入 `docs/audits/`。

2
/dev-plan

把确认后的发现转成单一路线计划。未决产品或数据语义先让用户确认。

3
/dev-branch

实现修复，在审核前关闭或归档相关 audit/plan，并更新 capability、ADR 或测试。

分支闭环：同一次任务只做一个可解释 diff

`dev-branch` 不要求工作区绝对干净，但要求改动可归属。相关 plan/audit 可以带入任务分支，无关源码或配置改动必须先停下询问。

Changelog Gate

影响用户、操作者、公开行为、数据、安全、安装、配置、兼容性或发布说明时，更新 `CHANGELOG.md`。

Distill Gate

任务改变长期知识、ADR、context-map、测试或 plan/audit 生命周期时，在审核前一起处理。

Check Gate

文档或生命周期产物发生变化时，先验证 audit、plan、ADR、CHANGELOG 和路由状态。

Review Gate

展示 `git status` 和 `git diff`，用户明确批准后才提交、合并、删除分支。

审核输出必须包含什么

审核不是一句“改好了”。它要让用户能判断这批 diff 是否可以进入主分支。

The canonical branch response shape lives in skills/dev-branch/templates/output.md. Use Before Approval before commit or merge approval, and After Merge only after the approved merge and cleanup complete.

skills/dev-branch/templates/output.md
Branch: task/YYYYMMDD-short-task-slug

Existing changes before branch:
- ...

Changes made:
- ...

Verification:
- ...

Changelog gate:
- Updated CHANGELOG.md under [Unreleased]
- or Not needed: <reason>

Distill gate:
- Updated CONTEXT/capabilities/ADR/context-map/tests/lifecycle artifacts
- or Not needed: <reason>

Check gate:
- Passed: <command/result>
- or Not needed: <reason>

Review:
- git status --short --branch --untracked-files=all
- git diff

Waiting for approval:
- Say "审核通过" or "可以合并" to let me commit, merge, and clean up.
- Push will not be performed unless separately requested and confirmed.
