工作流

从模糊需求到可审核合并

Dev Flow 把任务拆成一组门控。每个门控都有明确职责，避免智能代理跳过决策、混入无关改动或把一次性报告当成长期知识。

日常开发 技能依赖图 步骤输出 审查驱动 分支闭环 审核输出

日常开发：brainstorm -> plan -> branch

模糊需求先由 /dev-brainstorm 澄清目标、非目标、方案和决策；涉及大文件或模块边界时先用 /dev-split 明确代码放置约束；明确任务由 /dev-plan 创建计划；/dev-branch 负责实现、验证和审核前收尾。

计划
/dev-plan->上下文门控->决策门控->计划文件或会话计划
拆分
/dev-split->边界门控->责任模块和约束

收尾

技能依赖图：什么时候接入哪个技能

这张图把用户请求先分流，再进入计划和实现。它的重点是避免 Agent 跳过前置判断：模糊需求先澄清，结构风险先约束，审查任务先产出 finding。

1. 请求入口用户给出想法、bug、审查问题、重构目标或明确任务。
2. 前置分流dev-brainstorm 处理模糊目标；dev-audit 处理有边界审查；dev-split 处理大文件和模块边界风险。
3. 执行计划dev-plan 汇总事实源、决策点、拆分约束、步骤和验证方式。
4. 分支实现dev-branch 创建任务分支，只实现确认路线，并遵守责任模块约束。
5. 审核闭环更新日志、知识沉淀、校验、独立评审全部完成后，才等待用户审批。
dev-split 的位置：它不是实现步骤，而是结构边界门控。它输出“不拆分、局部整理、延后处理或建议拆分”，并告诉计划“新代码应该放哪里、不要放哪里”。

文档产物流向

当前事实CONTEXT.md、docs/capabilities/、DESIGN.md 只保存当前有效规则。
过程证据docs/plans/ 和 docs/audits/ 驱动当前任务；结束后 archive、delete 或保持 active 并说明原因。
长期决策docs/adr/ 只记录难反悔、有真实取舍的长期决策。
发布说明CHANGELOG.md 只记录用户、操作者、安装、配置、兼容性、安全或公开行为变化。

每一步最后输出什么

Dev Flow 的重点不是多跑几个命令，而是让每个阶段留下可审查的结果。用户可以从输出判断下一步是否能继续，Agent 也能从产物继续接力。

阶段内部经历最终输出可继续条件
/dev-orient读取 AGENTS、CONTEXT、context-map、相关 capability 和代码入口。上下文来源、相关入口、文档目的地、推荐下一技能。事实源明确，下一步路由清楚。
/dev-brainstorm低噪声进入上下文、澄清目标/非目标、比较方案、确认用户决策。确认路线、决策点、备选方案、下一技能。目标和关键决策已确认，或明确停下提问。
/dev-split扫描并评估大文件、模块边界、状态所有权和代码放置风险。不拆分、局部整理、延后处理或建议拆分；责任模块、约束、验证方式。计划中已有明确代码放置约束，或等待用户批准拆分方案。
/dev-plan上下文门控、决策门控、范围确认、步骤和验证设计。目标、范围、事实源、步骤表、验收标准、计划路径或阻塞原因。没有未决决策，步骤都有验证方式。
/dev-audit审查范围、证据读取、问题编号、严重度和状态判定。带编号、状态、证据、归属计划、验证方式的问题表，必要时写入 docs/audits/。每个问题有证据和后续路由。
/dev-branch创建分支、实现、验证、生命周期门控、独立评审、审批评审。变更摘要、验证结果、门控结果、子代理或人工评审、git 状态和差异摘要、等待审批说明。所有必要门控通过或明确不需要，且不存在评审阻塞项。
/dev-distill知识分类、ADR 门控、计划收尾、审查收尾、验证。长期文档更新、计划/审查生命周期结果、ADR 判断、下一步校验。未关闭产物保持 active；可关闭产物有明确原因。
/dev-check检查模板、文档路由、状态字段、归档目录和 git 可见性。错误、警告、建议、校验结果。无错误；警告有明确处理或接受理由。

审查驱动：audit -> plan -> branch

当任务是“看看哪里不对”时，先审查，不要直接写计划。审查报告只放在 docs/audits/，稳定事实由后续 distill gate 同步到长期文档。

1
/dev-audit

内置 orient gate，定义范围、读取证据、输出带 ID 和状态的 findings。非平凡审查写入 docs/audits/。

2
/dev-plan

把确认后的发现转成单一路线计划，并记录 source_audit、covered_findings 和 deferred_findings。

3
/dev-branch

实现修复，在审核前更新 finding 状态、验证结果和 branch/commit 关联；未全部关闭的 audit 继续保持 active。

分支闭环：同一次任务只做一个可解释 diff

/dev-branch skill 不要求工作区绝对干净，但要求改动可归属。相关 plan/audit 可以带入任务分支，无关源码或配置改动必须先停下询问。

更新日志门控

影响用户、操作者、公开行为、数据、安全、安装、配置、兼容性或发布说明时，更新 CHANGELOG.md。

知识沉淀门控

任务改变长期知识、ADR、context-map、测试或计划/审查生命周期时，在审核前一起处理；部分修复只能更新问题状态。

校验门控

文档或生命周期产物发生变化时，先验证审查、计划、ADR、CHANGELOG、输出模板和路由状态。

独立评审门控

有价值且可安全委派时使用只读子代理，否则执行同形状的人工评审；主代理复核问题并负责最终证据。

审批评审门控

展示 git status、变更文件和差异摘要，默认不输出完整差异；用户明确批准后才提交、合并、删除分支。

审核输出必须包含什么

审核不是一句“改好了”。它要让用户能判断这批 diff 是否可以进入主分支。

标准分支输出模板位于 skills/dev-branch/templates/output.md。提交或合并审批前使用 Before Approval 形态；只有在用户批准合并且清理完成后，才使用 After Merge 形态。

更新日志门控：
- 已在 CHANGELOG.md 的 [Unreleased] 下更新
- 或不需要：<原因>

知识沉淀门控：
- 已更新 CONTEXT、capability、ADR、context-map、测试或生命周期产物
- 或不需要：<原因>

校验门控：
- 已通过：<命令/结果>
- 或不需要：<原因>

独立评审门控：
- 模式：子代理/人工
- 计划符合性：通过/失败/不适用
- 审查覆盖：通过/失败/不适用
- 只包含相关改动：通过/失败
- 验证证据：通过/失败
- 阻塞项：无/<问题>

审核：
- git status --short --branch --untracked-files=all
- 变更文件和差异摘要

等待审批：
- 回复“审核通过”或“可以合并”后，才会提交、合并和清理。
- 除非单独请求并确认，否则不会推送。
